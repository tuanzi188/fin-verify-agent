# KnowledgeMind · 企业知识问答 Agent 与多维能力评测

> 项目设计文档 · v0.3 · 2026-10-27
> 状态：设计稿（待实施）
> 一句话：一个企业知识问答 Agent，外加一套 30 条任务的五维能力评测；不是两套测评集，是一套任务集看五个能力维度。
>
> 对外短标题可以叫「Agent 检索工具与评测」；但内部口径以本文档为准：一个 Agent、一套任务集、五个维度、一份能力剖面。

---

## 1. 项目定位

### 1.1 它是什么

**一个项目，两条主线，一个共用底座：**

| 部分 | 角色 | 产出 |
|---|---|---|
| **Agent 线（被测）** | 企业知识问答 Agent | 答案 + 引用 + 状态（answered / abstained / clarified / error）+ 轨迹 |
| **评测线（考官）** | 一套 30 条任务、五个能力维度 | 能力剖面 + 失败分类 + badcase + 回归门禁 |
| **工具层（底座）** | Agent 可调用的检索/回查/文档浏览能力 | 进程内只读工具；MCP 为可选适配层 |

它不是“两个项目拼起来”，也不是“两套并列的测评集”。评测线只有一套任务集，只是从五个能力维度去观察同一个 Agent。

### 1.2 它不是什么

- **不是两套测评集**：没有“检索 suite + Agent suite”两套并列的题库；只有一套 30 条任务，每条任务自带检索诊断字段。
- **不做 dev/test 切分**：30 条切出 10 条 test 后每维只剩 2 条，统计上无意义（2/2 的 Wilson 下界仅 34%）；控过拟合改用**整卷配对差分 + 版本冻结**，且差分必须 ≥3 次/任务（见 §9.3 / §8.13）。
- **不是通用 Agent benchmark 平台**：只评本项目的 Agent 与工具，不做排行榜、不做多框架适配。
- **不是刷榜项目**：不追求 SOTA 分数，追求口径可复述、结果可追溯、结论能驱动决策。
- **不是通用助手**：不做写操作（建工单、发邮件）、不做多租户、不做大规模并发。
- **不是 dashboard 项目**：先有 JSON 报告与能力剖面，HTML/前端页面是附带的。
- **不是“单次成功就算过”**：非确定性显式处理，每任务 3 次，每次报 pass@1；pass^3 只在全量报告产出。

### 1.3 与现有项目的关系

在现有 KnowledgeMind（企业 RAG 知识库）上升级，不重写：

- 保留文档解析、混合检索、RRF 融合、Cross-Encoder 精排、引用回查、身份隔离、Docker 部署。
- 把“固定 RAG 链路”升级为“会决策的问答 Agent”：是否检索、检索几次、是否回查、是否拒答、是否澄清、何时停。
- 新增一套 30 条任务的五维评测、能力剖面、失败分类、分层 CI（夹具 + 冒烟必跑，全量手动）。
- 现有 60 条 query 的检索评测降级为**工具层回归夹具**，只在 CI 跑，不进入主叙事。

## 2. 背景与问题

### 2.1 市场问题

Agent 的 demo 已经泛滥：接一个大模型、挂两个工具、跑通一条链路，就能叫“Agent”。但真正决定 Agent 能不能用的是：

- 工具选得对不对；
- 参数填得对不对；
- 多步任务里会不会丢上下文；
- 工具报错/空结果时会不会恢复；
- 该拒答时会不会编造；
- 问题含糊时会不会追问；
- 成本和延迟是否可接受。

这些问题，靠“演示一遍成功案例”回答不了，只能靠**可重复、分维度的评测**回答。会做 Agent 的人多，能说清“哪一维不行、为什么不行”的人少。

### 2.2 现有项目的问题

现有 KnowledgeMind 已经有一套不错的检索评测：

- 60 条 query / 6 类场景；
- 4 种召回 × 4 档重排对照；
- 负结果：三路融合相对单路向量只有 +1.8pt，增益主要来自重排；
- 拒答评测、失败归因、CI 回归门禁。

但它评的是“检索链路”，不是“Agent 行为”。它不能回答：

- Agent 会不会在该调用工具的时候调用？
- 工具选错时，是工具描述问题还是模型问题？
- 多步任务里，第二步会不会忘了第一步的文档？
- 换一种 Agent 实现，任务成功率、步数、成本会变多少？
- 哪个能力维度是短板，该优先改哪里？

### 2.3 机会

把“检索评测”的方法论延伸到“Agent 多维能力评测”，形成：

- **一套任务集**：30 条任务，同时带行为标签与检索标签；
- **五个能力维度**：检索与引用、多步拆解、拒答与边界、澄清与追问、恢复与纠错；
- **一份能力剖面**：每个维度一个分数 + 95% CI，不合成总分；维度只做看板；
- **一套失败归因**：区分召回失败、工具选择错误、参数错误、丢上下文、编造等；
- **一套回归门禁**：硬门禁（编造 / 引用错误 / 崩溃 / 延迟）+ 稳定性；维度只做看板。

这正是当前简历市场里稀缺的能力：**能定义并测量 Agent 好不好用。**

## 3. 项目目标

### 3.1 能力目标

1. Agent 能回答企业知识问题，答案带引用，知道什么时候该拒答、什么时候该追问。
2. 评测能给出一张**五维能力剖面**，而不是一个总分。
3. 评测能区分失败是“召回问题”还是“Agent 决策问题”。
4. 能对比 baseline 与 improved 两个变体，回答“改了什么、哪一维涨了、成本涨了多少”。
5. 评测本身可回归：硬门禁跌破、稳定性下降，CI 直接拦住。

### 3.2 可量化目标

绝对分数不在设计阶段写死：n=6/维，绝对值没有解释力。本节定义的是**每个阶段结束时必须拿得出的可量化产出**。

**阶段判据**

| 阶段 | 可量化判据 |
|---|---|
| 阶段 2（baseline） | 五维各有 1 个点估计 + 95% CI；失败分布覆盖 ≥5 类；30 条任务全部通过 lint（§9.4） |
| 阶段 3（improved） | 至少 1 维有可分辨 delta（delta ≥ 该维 CI 宽度），或明确给出否定结论；同时报 token / 延迟成本差 |
| 阶段 4（CI） | 硬门禁全部可自动判定并返回退出码；12 条冒烟 100% 绿 |
| 阶段 5（对外） | 每个对外数字都能指到报告文件的某一行 |

> “可分辨”= delta ≥ 该维 Wilson CI 宽度。n=6 时 CI 宽度约 50pt，所以多数维度会得出“不可分辨”——**这是正常结论，不是失败**。

**五个能力维度的测量产出**

| 维度 | 核心指标 | 产出形态 |
|---|---|---|
| 检索与引用 | 引用存在率、引用正确率、答案要点覆盖、recall@k 诊断 | 点估计 + CI + 失败归因 |
| 多步拆解 | 任务成功、子问题覆盖、平均步数 | 点估计 + CI + 步数分布 |
| 拒答与边界 | 拒答正确率、编造率、误拒率 | 计数式（零容忍项）+ 点估计 |
| 澄清与追问 | 澄清触发率、误澄清率、追问相关性 | 正负对照双向计数 |
| 恢复与纠错 | 尝试恢复率、恢复成功率 | 点估计 + CI（自评三项为诊断明细，不进剖面） |

**横切指标**

| 指标 | 产出形态 |
|---|---|
| 平均步数 / 中位步数 | 两变体对比 |
| 延迟 | median + max 进硬门禁；分位数进看板 |
| token 成本 | 每任务均值 + 两变体差额 |
| pass@1 | 每次运行都报 |
| pass^3 | 仅全量报告产出（3 次/任务），日常迭代不比 |

> 具体门槛等 baseline 跑出来后设定（规则见 §8.6、§8.9）；没有 baseline 不写死数字。

### 3.3 非目标

- 不做两套并列的测评集；
- 不做通用 benchmark、排行榜、多框架适配；
- 不把五个维度合成一个总分；
- 不做写操作、多租户、生产级高可用；
- 不追求大规模语料，追求任务设计质量；
- 不把 LLM-as-judge 当唯一判分依据；
- 不先做 dashboard。

## 4. 用户与场景

### 4.1 目标用户

- 要把企业知识库接进 Agent 的应用工程师；
- 要评估 Agent 选型、prompt、工具描述、模型变更的团队；
- 面试官 / 评审者：想快速判断项目是否真的“可评测、可追溯”。

### 4.2 典型场景

1. **接入**：Agent 在进程内直调检索工具，完成“检索 → 回查 → 回答”。
2. **看剖面**：跑 30 条任务，得到五个维度的能力剖面，定位短板。
3. **选型**：对比 baseline 与 improved，看哪一维涨了、成本涨了多少。
4. **回归**：改 prompt、改工具描述、换模型后，跑同一套评测，看维度是否回退。
5. **归因**：任务失败时，区分召回失败、选错工具、参数错、丢上下文、编造。

## 5. 功能范围

### 5.1 工具层（共用底座）

**核心功能**

- 检索工具：按自然语言查询返回相关段落，含标题、文档、片段、相关性分数。
- 回查工具：按段落 ID 返回原文、出处、所属章节。
- 文档浏览工具（可选）：按文档 ID 返回目录/章节列表，支持多跳任务。
- 传输：stdio（本机客户端）与 streamable-http（远程/多客户端）。
- 客户端示例：一个最小 Agent，跑通“检索 → 回查 → 回答”，并打印步数、耗时、token。

**工具设计原则**

- 工具名、描述、参数结构、返回结构集中管理，MCP server 与 Agent runner 共用，避免两份实现漂移。
- 工具描述是 Agent 的“使用说明书”，要写清：什么时候用、参数范围、返回什么、什么情况下应该停止或拒答。
- 工具描述纳入版本管理，作为评测变量之一；改描述要跑评测。
- 工具不做隐式重试、不做隐式改写，保持行为可预测；重试与改写属于 Agent 层策略。

### 5.2 Agent（被测）

**功能定位**

企业知识问答 Agent，不是通用助手。它拿到一个制度/流程/规定类问题，决定：

- 要不要检索；
- 检索一次还是多次；
- 要不要回查原文；
- 要不要引用；
- 资料不足时拒答，还是换个 query 再试；
- 问题含糊时追问，还是说明假设；
- 什么时候停，避免无限循环；
- （可选）答完是否自评：引用是否支持、数字是否一致、证据是否足够。

**两个变体**

| 变体 | 行为 | 用途 |
|---|---|---|
| **baseline** | 单次 function calling，最多一次检索，无自评 | 作为对照基线 |
| **improved** | ReAct + 自评 + 重试/拒答/澄清 | 证明多维评测能驱动改进 |

> 只有一版的话，能力剖面只是体检报告；两版对比才有“改了什么、哪一维涨了、成本涨了多少”的决策结论。

**输出契约**

答案 + 引用 + 状态（answered / abstained / clarified / error）+ 轨迹。轨迹的具体字段在 §6.5 冻结，它是判分的唯一数据源，比任务集 schema 更早定版。

### 5.3 一套任务集，五种观测

- **30 条任务 = 5 个能力维度 × 6 条**，只维护一套题库。
- 每条任务同时带两类字段：
  - **行为字段**：工具约束（非精确序列）、必填参数、答案要点、是否应拒答、澄清模式、最大步数；
  - **检索字段**：相关 chunk id、查询类型，用于失败归因。
- 一条任务只归一个**主维度**，可带副标签；报告按主维度汇总，不重复计数。
- 检索诊断不单独成集：Agent 跑完，把它的检索结果与任务里的相关 chunk 对一下，就能判断失败是召回还是决策。
- 任务集与语料分离：任务引用文档/片段，不把原文内联进任务。

### 5.4 工具层回归夹具

- 现有 60 条 query / 6 类场景保留，但降级为**工具层回归夹具**：
  - 只进 CI，不进主报告、不叫第二套测评集；
  - 4 种召回 × 4 档重排的对照留在这里，因为 30 条任务撑不起重排矩阵的分辨率；
  - 作用：保护工具层，回答“召回/排序有没有回退”。
- 主叙事只讲 30 条任务的五维能力剖面。

### 5.5 报告

- **必需**：JSON 报告，含逐任务明细、五维汇总 + 95% CI、失败分类、badcase 清单、横切指标、硬门禁结果。
- **推荐**：静态 HTML 报告，展示能力剖面、分维度表、失败分类表、baseline vs improved 对比。
- **可选**：在现有 React 前端增加 Eval 页面；不先做。
- **不做**：单一总分。总分会把 trade-off 藏起来。

## 6. 总体架构

### 6.1 两条主线 + 一个底座

| 层 | 职责 | 主要产出 |
|---|---|---|
| 工具层 | 检索、回查、文档浏览；进程内只读工具（`app/tools/`） | 与 Agent 同进程的工具函数，返回结构固定、失败可归因 |
| Agent 线 | 选工具、填参数、多步执行、生成答案、自评 | 答案 + 引用 + 状态 + 轨迹 |
| 评测线 | 任务集、判分、维度汇总、报告、回归 | 能力剖面 + 失败分类 + badcase + 门禁结果 |

> **MCP 只是工具层的可选适配器**（`app/mcp/server.py`），给 Cursor / Claude Desktop 这类客户端接入用，**不进评测主线**。评测走进程内直调：协议层会把序列化与进程通信耗时混进 `latency_ms`，让"Agent 多调了一次工具"和"传输慢"分不开；故障注入在协议层也难以精确控制。

### 6.2 数据流

任务集 → 评测 runner → Agent → 工具调用 → trace 记录 → 判分（确定性 + rubric/judge）→ 五维汇总 → 能力剖面 → CI 门禁 → badcase 回灌任务集。

### 6.3 模块边界与契约

| 模块 | 拥有什么 | 不许做什么 |
|---|---|---|
| **agent** | Agent 循环、prompt、工具选择、自评逻辑、配置 | 不许 import 评测代码；不许知道任务集的判分规则 |
| **tools** | 检索、回查、文档浏览（MCP server 为可选适配） | 不许内置 Agent 逻辑；不许依赖评测 |
| **eval** | 任务集、runner、judge、指标、报告、baseline、CI | 不许 import Agent 内部实现；只能通过契约/CLI 调用 |

**契约**：Agent 对外只暴露一个入口，输入任务，输出 `answer + trace + usage + status`。评测只认这个入口，不 import Agent 的 prompt、loop、内部函数。

**隔离级别**（推荐程度从高到低）：

1. **进程隔离**：eval 用 CLI 调 agent，任务 JSON 进、结果 JSON 出。最像黑盒，最容易换 Agent。
2. **契约模块隔离**：eval 只 import `agent.contract`（数据类型 + 入口），不 import `agent.runtime`。轻量，但靠纪律。
3. **同进程直接 import**：最省事，但最容易偷偷依赖内部实现，不推荐做评测。

**隔离验证**：

- 一条 import 边界测试：`eval` 不能 import `agent.runtime`，`agent` 不能 import `eval`；违反即 CI 失败。
- 一个 stub agent：eval 能对一个“只回显问题”的假 Agent 跑通全流程，证明它不依赖真实现。

### 6.4 模块划分

| 模块 | 职责 |
|---|---|
| 工具实现 | 检索、回查、文档浏览的实际逻辑与返回结构 |
| MCP server（可选） | 只做协议适配与 transport，不内置 Agent；不进评测链路 |
| Agent runner | baseline / improved 的统一入口，输出答案与轨迹 |
| 任务集 | 30 条任务的定义、主维度、难度、期望行为、检索标签 |
| 判分器 | 确定性检查、rubric、LLM judge、人工抽检 |
| 报告器 | JSON / HTML 报告，五维剖面与失败分类 |
| 回归器 | baseline 对比、硬门禁、CI 退出码 |

### 6.5 轨迹契约（trace schema）

评测的确定性检查几乎全部吃 trace，因此 trace 必须先于任务集冻结。Agent runner 与 eval 之间传的就是它；进程隔离（§6.3 第 1 级）跑完后，eval 只剩这个 JSON 可用。

```json
{
  "task_id": "T19",
  "variant": "improved",
  "run_index": 1,
  "status": "answered",
  "answer": "……",
  "citations": [{"marker": 1, "chunk_id": "hr-003#2"}],
  "trace": [
    {"step": 1, "tool": "search_kb", "args": {"query": "出差住宿标准", "top_k": 5},
     "ok": true, "result_ids": ["hr-003#2", "hr-003#3"], "result_count": 2,
     "injected": null, "latency_ms": 210, "tokens_in": 0, "tokens_out": 0},
    {"step": 2, "tool": "get_citation", "args": {"chunk_id": "hr-003#2"},
     "ok": true, "result_ids": ["hr-003#2"], "result_count": 1,
     "injected": null, "latency_ms": 80, "tokens_in": 0, "tokens_out": 0},
    {"step": 3, "tool": "__final__", "args": {},
     "ok": true, "result_ids": [], "result_count": 0, "injected": null,
     "self_eval": {"triggered": true, "verdict": "pass", "reason": "引用覆盖要点①②③"}}
  ],
  "usage": {"steps": 2, "tokens_in": 812, "tokens_out": 96, "latency_ms": 1240}
}
```

**字段约束**

| 字段 | 必填 | 说明 |
|---|---|---|
| `trace[].tool` | 是 | 工具名；终止步统一用 `__final__`，便于计数 |
| `trace[].args` | 是 | 原样记录，供参数检查 |
| `trace[].result_ids` | 是 | 返回的 chunk id 列表；工具步为实际返回，`__final__` 填 `[]`；只记 id 不记正文 |
| `trace[].injected` | 是 | 工具步填注入类型（`empty` / `timeout` / `500` / `truncated` / `null`），`__final__` 填 `null`；Agent 不可见 |
| `trace[].self_eval` | 否 | 仅自评发生的步上有：`triggered` / `verdict` / `reason` |
| `status` | 是 | `answered` / `abstained` / `clarified` / `error`，四态互斥 |
| `variant` / `run_index` | 是 | 报告按这两维分组；缺任一个都无法算 pass^3 |

> `__final__` 步也必须带 `result_ids: []` / `result_count: 0` / `injected: null`，保证每步结构一致，判分代码不用按工具名分支。

**约定**

- `usage.steps` 不含 `__final__` 步；token 分工具侧与生成侧，报告分列。
- `result_ids` 只记 id：正文由 `get_citation` 或语料侧回查，避免 trace 与语料漂移。
- `injected` 由工具层写入，Agent 侧不得写；否则注入计划会泄漏进上下文，恢复维度就不成立。
- 改这个契约必须重跑 baseline，否则新旧报告的指标不可比。

### 6.6 HTTP 入口：复用 `/chat`，不新开端点

Agent 没有单独的路由。**复用现有 `POST /api/v1/chat`**，靠 `mode` 分流：

```
POST /api/v1/chat
{ "query": "...", "conversation_id": "...", "mode": "rag" | "agent", "max_steps": 3 }
```

| 复用项 | 说明 |
|---|---|
| 鉴权 | 仍由 `verify_api_key` 依赖统一挂载 |
| 用户上下文 | `extract_user_context` → 传给 Agent 工具层做 ACL |
| 会话隔离 / 落盘 | `ConversationNamespace` + `conversation_memory.add_turn` |
| 审计 | 复用 `CHAT_QUERY`，`details.mode` 区分 |
| 响应模型 | `ChatResponse` 增加可选 `status / trace / variant / duration_ms`；RAG 路径为 null |

**三条硬约束**：

1. **ACL 必须下沉到工具层**：`search_kb` / `get_citation` 接受 `user_context`；`None` 表示评测/内部调用（不过滤），线上入口必须传。只在 API 层过滤不够——模型上下文里已经看过了。
2. **请求体禁止故障注入**：`ChatRequest` 设 `extra="forbid"`，`mock` / `inject` 只存在于评测任务卡，不能从公网打开。
3. **v1 非流式**：`/chat/stream` 遇到 `mode=agent` 直接 400；不要让客户端以为在用 Agent。等待期 UI 显示“正在多步检索”。

**已知限制**：单轮（不继承历史）、无独立限流、产品路径比评测路径多一层 ACL 与引用补全。

## 7. 关键设计决策

1. **一个项目、两条主线、一个底座**：不是两个项目拼起来，也不是两套测评集。
2. **一套任务集，多维观测**：30 条任务同时带行为标签与检索标签；检索诊断内嵌，不另起一套题库。
3. **维度是能力，指标是测量**：五个维度回答“哪方面强/弱”，指标回答“强多少/弱多少”；不把两者混成一个分数。
4. **不合成总分**：总分会掩盖 trade-off（比如多跳强但成本翻倍）；用硬门禁 + 维度剖面，不给单一分数。
5. **工具与 Agent 解耦**：工具层只提供工具，Agent runner 是调用方；同一工具可以换不同 Agent 对比。
6. **两个变体才有决策价值**：baseline 与 improved 对比，才能说明“改进带来了什么、代价是什么”。
7. **确定性检查优先**：工具选择、参数、是否调用、是否拒答，能用代码判的绝不交给 LLM judge；LLM judge 只判开放答案。
8. **非确定性显式处理**：每任务跑 3 次，每次报 pass@1；pass^3 只在全量报告产出。不接受“跑一次成功就算成功”。
9. **CI 分层**：PR 跑 12 条冒烟（1 次）+ 检索夹具；全量（30 任务 × 3 次 × 2 变体）在发版前手动跑。
10. **失败分类先于总分**：总分只回答“好不好”，失败分类回答“哪里不好、该改什么”。
11. **工具描述版本化**：工具描述是 prompt 的一部分，改描述等于改 Agent 的输入；每次改都要跑评测。
12. **评测可追溯，不承诺逐位复现**：固定 temperature，记录模型版本、工具描述版本、任务集版本、语料 hash、变体名；报告里带全部运行参数。API 模型版本会漂移，“同一口径”可保证，“完全一样”不承诺。

## 8. 评测口径

### 8.1 五个能力维度

| 维度 | 任务数 | 考什么 | 核心指标 | 典型失败 |
|---|---:|---|---|---|
| **检索与引用** | 6 | 能不能找到并引用原文 | 引用正确率、答案要点覆盖、recall@k 诊断 | 编造出处、引错段 |
| **多步拆解** | 6 | 能不能拆子问题、保持上下文 | 任务成功、子问题覆盖、平均步数 | 只答一半、丢上下文 |
| **拒答与边界** | 6 | 资料不足时会不会编 | 拒答正确率、编造率、误拒率 | 编造、过度拒答 |
| **澄清与追问** | 6 | 问题含糊时会不会问，不该问时会不会乱问 | 澄清触发率、误澄清率、追问相关性 | 硬答、问无关、过度追问 |
| **恢复与纠错** | 6 | 空结果/报错/自评后会不会修正 | 剖面：尝试恢复率、恢复成功率；明细：自评触发率、自评准确率、修正成功率 | 卡死、越改越错 |

**横切指标**：平均步数、延迟（median / max / P95）、token 成本、pass@1（每次）/ pass^3（仅全量）。

> 维度分数只做**看板与诊断**，不做百分比门禁；CI 门禁只设在零容忍/确定性项上（见 §8.6）。
> **剖面指标 = 两个变体都能算、可直接比较的指标**。恢复维度只有「尝试恢复率」「恢复成功率」进剖面；自评三项只在 improved 上统计，属于**诊断明细**，不进剖面表面——否则 baseline 那两格是 N/A，五维剖面就不可比了。

### 8.2 指标定义

**维度指标**

| 指标 | 定义 | 判定方式 |
|---|---|---|
| 引用存在率 | 答案是否带引用；只判有无，不判对错 | 确定性检查 |
| 引用正确率 | 引用 chunk 是否真的支撑对应 `answer_point`；逐点核验 | 确定性检查 + 人工抽检 |
| 答案要点覆盖 | 必答要点覆盖比例 | rubric |
| recall@k 诊断 | 任务相关 chunk 是否出现在 Agent 的检索结果前 k 条 | 确定性检查 |
| 任务成功 | 答案满足 rubric 且工具行为正确 | 确定性检查 + rubric |
| 子问题覆盖 | 多跳任务的子问题完成比例 | rubric |
| 拒答正确率 | 负样本正确拒答、正样本不误拒 | 确定性检查 |
| 编造率 | 无依据的事实/数字/条款占比 | 确定性检查 + judge |
| 歧义处理正确率 | `clarify_mode=ask` 的任务中，Agent 追问 **或** 把两种情形各自的结论都给出的比例 | **judge**：判“有没有静默选边”，不判“有没有问号 / 有没有写取决于”；关键词实测漏判/误判各 1/3，不能用作指标 |
| 误澄清率 | `clarify_mode=none` 的任务中，Agent 不该问却问的比例 | **judge**：同上，关键词不可靠 |
| 澄清代价 | ask 任务的两种情形必须给出**不同**结论（静默选边会答错） | 任务设计：没有代价的歧义只能测措辞 |
| 尝试恢复率 | 注入故障后，Agent 是否至少尝试重试/改写/换工具 | 轨迹 |
| 恢复成功率 | 尝试恢复后，最终答对的比例 | 轨迹 + 结果 |
| 自评触发率 | 自评实际触发的任务比例（manipulation check） | 轨迹 |
| 自评准确率 | 自评能拦住错误答案、放行正确答案的比例 | 外部 ground truth 对比 |
| 修正成功率 | 自评触发后，修正是否真的变好 | 前后对比 |

> **剖面指标 vs 诊断明细**：进五维剖面的只有两变体都能算的指标——恢复维度是「尝试恢复率」「恢复成功率」。自评三项仅用于 improved 的诊断明细表，避免剖面出现 N/A。

**横切指标**

| 指标 | 定义 |
|---|---|
| 平均步数 | 每条任务的平均工具调用次数 |
| 中位延迟 / max 延迟 | 端到端延迟的中位数与最大值，进硬门禁 |
| P95 延迟 | 端到端延迟的 95 分位；只进看板——n=30 时由 1–2 个样本决定，不稳 |
| token 成本 | 输入 + 输出 token 总量 |
| pass@1 | 单次运行通过率的均值（3 次取任务均值，不是只看第一次）；每次运行都报 |
| pass^3 | 三次运行全部成功的比例；**仅全量报告产出**，日常迭代不比 |

### 8.3 判分流程

**分工是硬边界**：机器能判的绝不给 judge，语义能判的绝不靠字符串匹配。

| 步骤 | 判什么 | 实现 | 判不了的下场 |
|---|---|---|---|
| 1. 确定性检查 | 工具四项约束、相关 chunk 是否进过结果、`[n]` 能否解析、每个要点是否被引用、引用是否来自检索结果、状态 vs `should_abstain`、步数预算、注入是否触发、注入后是否继续尝试 | `evaluation/agent_checks.py` | 不判就会把"没调工具"记成"答得不好" |
| 2. rubric + judge | 每个要点是否被覆盖、被引段落是否真的支撑该要点、是否出现 `forbidden`、澄清行为对不对、回答是否有据 | `evaluation/agent_judge.py`，原文从语料回查 | 交给字符串匹配 = 假客观 |
| 3. 维度判定 | 每维 pass / fail / **NA** / **invalid** | `evaluation/agent_report.py` | 把 NA 记成 0 是最常见的假数据 |
| 4. 汇总 | 逐任务 → 分维度 + Wilson 区间 + 失败分类 + badcase | 同上 | 只出总分就看不见 trade-off |
| 5. 人工抽检 | 随机样本复核，报与 judge 的一致率 | 手动（P4 排期） | judge 偏差无人校准 |

**四种判定结果**（不要混）：

- `pass` / `fail`：进分母；
- `na`：judge 不可用，**不进分母**；
- `invalid`：注入没触发，这一轮不是有效样本，**不进分母**。

**判分器的三条禁令**：

1. `required_args` 不判字面关键词——语义覆盖由"相关 chunk 是否命中"间接验证，命不中才退回 judge；
2. 引用正确率不判"有没有 `[n]`"，判"该要点是否被引用 + 被引段落是否支撑它"，逐点给证据；
3. judge 失败、解析失败、注入未触发，一律记 NA/invalid，**绝不当成 0 分**。

### 8.4 能力剖面与看板

**不做单一总分，也不做百分比维度门禁。** 维度分数是看板，不是上线判据。

| 维度 | 看板（示例） | 95% CI（示例） | 是否设门禁 |
|---|---|---|---|
| 检索与引用 | 83%（5/6） | [43.6%, 97.0%] | 否 |
| 多步拆解 | 67%（4/6） | [30.0%, 90.3%] | 否 |
| 拒答与边界 | 83%（5/6） | [43.6%, 97.0%] | 否 |
| 澄清与追问 | 50%（3/6） | [18.8%, 81.2%] | 否 |
| 恢复与纠错 | 67%（4/6） | [30.0%, 90.3%] | 否 |

> 横切：平均 2.8 步 / 中位 2.4s / max 5.8s / P95 3.1s / 1.8k token / pass^3 0.83。
> 以上数字是示例，等 baseline 跑出来后填真实值。

- 6 条/维度只能看趋势，不能当统计显著；报告里标注“诊断用途，n=6”，并给出 95% CI。
- baseline 与 improved 各出一张剖面，并排对比。
- 剖面只含两变体都能算的指标；自评三项属 §8.2 的诊断明细，不进此表（否则 baseline 出现 N/A，可比性被破坏）。
- 硬门禁见 §8.6：只设在零容忍/确定性项上。

### 8.5 失败分类

| 类型 | 定义 | 典型例子 |
|---|---|---|
| 召回失败 | 相关 chunk 没进检索结果 | 资料在库里但没搜到 |
| 选错工具 | 该回查却重新检索，或反之 | 需要原文却只给摘要 |
| 参数错误 | 必填参数缺失、越界、语义错 | top_k 超限、查询词丢限定 |
| 漏调用 | 该调工具却直接回答 | 没检索就编答案 |
| 多步丢上下文 | 后续步骤忘了前面的文档/约束 | 第二步引用了不存在的段落 |
| 过早结束 | 只完成部分子问题 | 多跳任务只答一半 |
| 过度拒答 | 资料存在却拒答 | 明明有制度却答“未提及” |
| 编造 | 资料没有却给出具体事实/数字 | 编造金额、日期、条款 |
| 自评漏判 | 自评没发现错误答案 | 引用不支持却放行 |
| 自评误判 | 自评把正确答案判错 | 正确引用被拦下 |
| 修正引入新错误 | 重试后改了但改错 | 数字改对、出处改错 |
| 预算超限 | 步数 / token / 延迟超上限 | 循环 10 步仍未收敛 |

### 8.6 评测效度与样本量

**先算账。** 95% Wilson 下界：

| 样本 | 点估计 | Wilson 95% 下界 |
|---|---:|---:|
| 5/6 | 83.3% | 43.6% |
| 6/6 | 100% | 61.0% |
| 7/8 | 87.5% | 52.9% |
| 8/8 | 100% | 67.6% |
| 11/12 | 91.7% | 64.6% |
| 12/12 | 100% | 75.8% |

结论：

- **n=6 连满分都过不了 70% 门槛**（6/6 下界 61.0%）；
- **n=8 满分 67.6%，也过不了 70%**；
- **n=12 错 1 条就掉到 64.6%**，必须 12/12 才够 75.8%。

所以 **70% 维度门禁在 n≤8 上不是“稳不稳”，是“数学上不可判定”**。

**硬门禁 vs 看板**

| 类型 | 指标 | 判定 | 说明 |
|---|---|---|---|
| 硬门禁 | 编造 | = 0 条 | 零容忍，出现即拦 |
| 硬门禁 | 正样本误拒 | = 0 条（或 ≤1 条） | 零容忍/计数式 |
| 硬门禁 | 引用错误 | ≤1 条（全量） | 计数式，不写“正确率 ≥80%” |
| 硬门禁 | 单步崩溃 | = 0 条 | 出现即拦 |
| 硬门禁 | 延迟 | median ≤3s 且 max ≤6s | n=30 时 P90/P95 都只由 1–3 个样本决定，不稳定；分位数放看板，门禁只认 median + max |
| 硬门禁 | 冒烟子集 | 全过 | 12 条冒烟必须全绿 |
| 看板 | 多跳成功率、澄清触发率、恢复成功率、pass^3 | 点估计 + 95% CI | 只报趋势，不设门禁 |

- 硬门禁是**工程政策**，不是统计陈述；用计数，不用百分比。
- 看板是**人看剖面**，报告点估计 + CI 宽度。
- 报告定位：**自动拦截硬伤 + 人看剖面**，不是“自动判定上线”。

**如果一定要保留维度门禁**：每维至少 8 条（总 40 条），且要求连续两次运行都低于阈值才告警。注意这**不会**让 70% 变得可判定（8/8 的下界也只有 67.6%），只是把点估计的抖动压小；它属于工程规则，不要包装成统计显著。

### 8.7 故障注入

恢复与纠错维度不能靠自然语料：真实空结果不会刚好 6 条，也不可复现。必须在工具层加故障注入。

**注入规则**

- 按 `(task_id, call_index)` 注入，模式：`empty` / `timeout` / `500` / `truncated`。
- Agent 看不到 mock，只看到正常的工具接口；注入计划不进入 Agent 的上下文。
- 任务卡加 `mock: true` 和 `inject` 字段；trace 记录每次注入。
- **mock 任务排除出召回诊断**：它的检索结果是人造的，不能用来算 recall@k，否则“召回失败”里会混进人造故障。

**共用接口，不共用响应**

- 60 query 回归夹具走**真实检索**，不能 mock；否则它就不是检索回归。
- mock 只用于故障注入，和真实工具共用同一套接口/返回结构。

**指标拆两个**

- **尝试恢复率**：注入故障后，Agent 是否至少尝试重试/改写/换工具。
- **恢复成功率**：尝试恢复后，最终答对的比例。

只报最终成功率，分不清“没试”和“试了没用”。

**示例分布**：6 条恢复任务 = 2 条 empty + 2 条 timeout + 1 条 500 + 1 条 truncated。

### 8.8 澄清反向对照

只有正向样本，Agent 学会“看到含糊就反问”就能刷满这一维。必须加反向对照。

**三态字段**：`clarify_mode: ask | assume | none`

- `ask`：确实缺关键条件，应该追问；
- `assume`：可以说明假设后直接答；
- `none`：表面含糊，但资料里能唯一确定，应该直接答。

**配比**：6 条澄清任务 = 3 正 + 3 负（至少 2 条负向对照）。

**反向例子**：“报销怎么走”——听起来缺主语，但制度里只有一种报销流程，正确行为是直接答；如果 Agent 反问，计**误澄清**。

**指标三个**：

- 澄清触发率：该问的问了；
- 误澄清率：不该问的没问；
- 追问相关性：问的是对的那个点。

只有第一个就是自欺欺人。

### 8.9 归因规则

**规则一：维度归因 ≠ 失败原因。**

- 维度分数按任务设计意图归主维度；一条多跳任务失败，分数仍计入“多步拆解”。
- 失败原因按实际原因全局统计；同一任务的真实原因可能是“第二跳空结果后没重试”，计入恢复类。
- 报告里两张表分开：维度剖面、失败分布；交叉表只做诊断，不用来改维度分数。
- 每条失败任务给主因 + 可选副因；统计按主因，副因只做参考。

**规则二：引用正确率要定义到判定链。**

- `引用存在率` 和 `引用正确率` 分开：有 `[1]` 不等于引用正确。
- 正确率 = 引用指向的 chunk 确实支撑对应 `answer_point` 的比例；判定锚点是任务里的 `answer_point.chunk_ids`，逐点核验、逐点给证据。
- 不要退化成字符串匹配；引用错段、引用无关内容都算错。

**规则三：门槛不能拍脑袋。**

- 先跑 baseline，再设门槛。
- no-regression 红线 = baseline 的 Wilson 下界。
- improvement 门槛 = baseline 点估计 + delta，且 delta ≥ baseline CI 宽度；否则不设门槛。
- n=6 时 CI 宽度很大，任何“+5pt 就上线”的说法都站不住；要么扩样本，要么只做硬门禁。

### 8.10 判分器稳定性

判分器自己也要被验证，否则分数是在测 judge 的心情。

**踩到的真问题（2026-10-27）**：同一份运行结果跑两批独立判分，30 条里 **2 条维度结论翻转**——
M2 从 fail 变 pass、V3 从 pass 变 fail，答案一字未改。

根因不是模型随机，而是**要点写得不够原子**：

| 任务 | 原要点 | 答案实际覆盖 | 两批判分 |
|---|---|---|---|
| V3 | 「离开工位超过十分钟须锁屏，**办公电脑需设置自动锁屏**」 | 只答了前半句 | 批 1 判 pass（盯时限）、批 2 判 fail（盯自动锁屏） |
| M2 | 「调整仅适用于 2026 年度及以后，**历史年度按原制度执行**」 | 分年度给了两个系数，没陈述规则 | 批 1 判 fail（没陈述）、批 2 判 pass（行为一致） |

**修法**：一条要点只放一个可判定的事实，并写进 lint 硬检查（§9.4 第 10 项）。

**修完复测**：两批独立判分，五维结论 **0 差异**；50 个要点 × 3 个标记 = 150 个判定里只有 1 个翻转
（还是个已失败要点上的 `cited` 标记，不影响维度结论）。批内重复判分（每任务 2 次）自一致率 0.99。

**三种"一致率"必须分清**：

| 指标 | 含义 | 本轮值 |
|---|---|---|
| 批内重复一致率 | 同一批里对同一答案判两次的吻合度 | 0.99 |
| 跨批判分一致率 | 两次独立判分的结论是否相同 | 修前 28/30，修后 30/30 |
| 与人工一致率 | judge 与人工复核的吻合度 | **未做，P4 排期** |

**别把前两个当第三个用**：自一致率高只说明 judge 稳定，不说明它判得对。
正确性只能靠人工抽检校准，这一点在报告里必须写清。

### 8.11 badcase 回灌

“评测驱动改进”如果没有机械流程，就只是一句口号。规则只有一条：

> **每次全量评测中，硬门禁失败或任一维度失败的任务，必须落成一条 badcase 记录；修复后该记录转为回归任务。**

记录字段：`task_id` / `run_index` / `主因`（§8.5 十二类之一）/ `证据`（trace 步号 + 引用原文）/ `修复动作` / `复测结果`。

- 主因必须落到 §8.5 的分类里，不许写“效果不好”。
- 只修不记账的改动不允许合并——否则同一个坑会踩第二次，而你没有证据。
- badcase 与任务集分开放（`eval/badcases/`）；修复后给任务标 `regression: true`，CI 冒烟层优先覆盖带此标记的任务。
- 每条 badcase 都是面试素材：它同时证明了评测能发现问题、以及你修了什么。

### 8.12 读数口径：哪些数字不是能力结论（2026-10-27 自检）

自检不看自己写的报告，只用 `runs` + `tasks` 重算，并逐条读 trace 与 judge 理由。
管线本身自洽（30 条样本、五维分母、门禁、token 与延迟都能对上），但**有两个维度
的数字会被误读**，必须在报告里跟数字一起出现：

| 现象 | 真实原因 | 处理 |
|---|---|---|
| 「恢复与纠错」baseline 只有 1/6 | baseline 定义就是**单轮**工具调用：首个调用失败后没有第二次机会。6 条里 4 条失败是构造性上限；唯一通过的 V3 是靠模型恰好并行发了两条 `search_kb`，第二跳成功——不是恢复策略在起作用 | 报告新增 `construct_notes`，写明"该维度在 baseline 上是设计对照，低分是预期"；improved 变体（多轮 + 重试）落地后才有可比结论 |
| 「澄清与追问」4/6 里的 2 条失败 | C2/C3 的答案把两种情形**都列全了**，只是没有明确说"请确认你是哪一种"——判据卡在措辞上，C1、C3 两批只差一句就翻转 | **同日已改**：`ask` 判定接受「明确追问」或「两种情形各自的结论都给出」，只有「只讲一种情形并当成用户答案」记 bad；C3 改成有时间成本的问题（“明天要在家办公，现在报备还来得及吗”），静默选边会答错。见 §8.2 |

**第三件事，也是自检里最难看的一条：单次剖面不稳定。**
同一份代码、同一温度（0.1）、同一任务集，前后跑两批 30 条：

| 维度 | 批 A | 批 B | 摆动 |
|---|---|---|---:|
| 检索与引用 | 5/5（1 条 judge 不可用→NA） | 5/6 | — |
| 多步拆解 | 6/6 | 5/5（1 条 judge 不可用→NA） | 0 |
| 拒答与边界 | 6/6 | 6/6 | 0 |
| 澄清与追问 | 2/6 | 5/6 | **+3** |
| 恢复与纠错 | 2/6 | 1/6 | −1 |
| 逐任务维度结论翻转 | **6/30 条**（C1/C3/C6/M3/R2/V4） | | |
| 答案文本逐字相同 | **0/30 条** | | |

6 条翻转里，**4 条是判定真的变了**（C1/C3/C6 澄清、V4 恢复），
**2 条是 judge 不可用造成的 NA**（M3、R2）。也就是说：Agent 随机性与判分器可用性
都会改变分母，"两批对比"本身也不能只比百分数。逐任务明细见
`docs/evidence/agent_stability_20261027.json`（含两批 runs 的 sha256 前缀）。

30 条答案**没有一条逐字相同**——温度 0.1 并不等于可复现（上游没有固定 seed）。
所以：

- 单次运行的剖面只能写"这一批长这样"，**不能当能力结论**；
- Wilson 区间只覆盖"从同一分布再抽 6 条"的抽样误差，**不覆盖 run-to-run 方差**；
  A 的 33.3% 与 B 的 83.3% 两个区间大幅重叠，正是这个原因；
- 每任务 ≥3 次并报 `pass^k` 是**必需品**，不是加分项。在此之前不许引用五维点估计做决策。

**修正后复测（同日）**：把 `ask` 判据改成“解释清楚歧义，不卡措辞”（§8.2）、把 C3 改成有代价的歧义、
judge 预算提到 4096 并加重试后，再跑两批：

| 指标 | 修正前 | 修正后 |
|---|---:|---:|
| 逐任务维度翻转 | 6/30 | **4/30**（C2/M2/R2/V4） |
| 其中 judge 不可用导致 | 2 条 | **0 条** |
| 澄清维度两批 | 2/6 vs 5/6 | **5/6 vs 6/6** |
| 答案逐字相同 | 0/30 | 0/30 |

4 条翻转全部是**答案内容差异**：C2 少给借调条件、M2 少说“仅适用 2026 及以后”、
R2 漏“三个工作日”时限、V4 靠并行第二次调用碰巧恢复——不是 judge 翻脸。
也就是说：**判分器口径修好了，Agent 的 run-to-run 方差还在**，`pass^k` 依然是必需品。
逐任务明细见 `docs/evidence/agent_stability_20261027_postfix.json`。

**另修掉三处口径错误（不是模型问题，是报告问题）**：

1. `judge: 调用 30 次` —— 实际是 30 条 × 2 次重复 = 60 次请求。新增
   `judged_tasks / repeats / llm_calls` 三栏，并注明一致率是**点级**而非整条通过率。
2. 失败原因直方图把一次失败的 3–4 个连带原因都算一遍，总数（18）超过失败条数（8）。
   现在同时给 `primary_count`（badcase 主因）与 `cooccurrence_count`（共现全景），并按主因排序。
3. 报告没有生成参数与代码版本，别人无法复现。`runs` 现在写 `run_config`
   （温度 / 终轮 token 上限 / 默认步数），`report` 写 `git.commit` + `dirty`。
4. judge 的 2048 token 预算不够：模型偶尔把预算全花在生成前的推理上，`content` 回来是空串、
   `finish_reason=length`，却被记成“解析失败”（一批 60 次里 6 次）。现在 judge 预算提到
   **4096**，并对 `length` 与解析失败各重试一次（`JUDGE_PARSE_ATTEMPTS=2`）；
   `failed_tasks`（整条不可判）与 `partial_failures`（靠剩余重复判完）分栏报告。
5. 客户端没设超时：一次任务挂了 **4,528,320 ms（75 分钟）**，整批跑了 78 分钟。
   SDK 默认 600s 读超时 × 自身重试 × provider 轮询，把最坏情况放大到小时级。
   现在 `AsyncOpenAI(timeout=120, max_retries=0)`，重试统一由 `retry_with_backoff` 负责。
   这条同时解释了为什么 `latency_max_ms` 曾出现 4.5e6 这种读数——不是模型慢，是请求挂死。

**顺带修掉的隐患**：`openai_client` 里 `temperature=temperature or model_cfg["temperature"]`
会把显式传入的 `0.0` 当成"没传"而换成档位默认值——评测里这意味着悄悄丢掉确定性设置。
改为 `is not None` 判断。

### 8.13 测量分辨率：这套题集能看见多大的差异

每维 6 条 → **1 条任务 = 16.7 个百分点**。这不是精度问题，是分辨率上限：

| 比较方式 | 最小可检出差异 | 算法 |
|---|---|---|
| 两批独立运行，每维 6 条 | **6/6 vs 1/6**（p=0.015）；5/6 vs 2/6 的 p=0.24，属噪声 | Fisher 精确检验 |
| 同一批任务跑两变体（配对，单维 6 条） | **6:0**（p=0.031） | McNemar 精确检验 |
| 同一批任务跑两变体（配对，整卷 30 条） | **21:9**（p=0.043） | McNemar 精确检验 |

**所以报告必须遵守三条**：

1. 分维度只报描述性数字与 Wilson 区间，**不做显著性宣称**；
2. 要检验“改进有效”，用**整卷 30 条配对**（同一批任务跑两变体），不要拿两批独立运行的百分比比；
3. 单次运行的剖面标注“单批快照，不可引用”。

报告里的 `resolution` 字段由 `evaluation/agent_report.py` 的 `build_resolution()` 自动算出，
任务数或每维条数变了门槛会跟着变，不是硬编码的示例值。

## 9. 数据与语料

### 9.1 一套任务集（30 条）

**结构**：5 个维度 × 6 条，只维护一套题库。

**每条任务字段**

| 字段 | 含义 | 示例 |
|---|---|---|
| `id` | 唯一 ID | T19 |
| `dimension` | 主维度 | 多步拆解 |
| `secondary_tags` | 副标签 | 引用、财务 |
| `difficulty` | easy / medium / hard | hard |
| `question` | 用户问题原文 | 出差住宿标准和报销流程分别是什么？冲突以哪个为准？ |
| `tool_constraints` | 工具约束四项：必含 / 调用次数范围 / 必要先后 / 禁含；不判精确序列 | `must_include:[get_citation]`、`call_count:{search_kb:[1,3]}`、`order:[[search_kb,get_citation]]`、`must_not_include:[list_documents]` |
| `required_args` | 必填参数：判子问题的**语义覆盖**，不判字面关键词 | 住宿标准、报销流程 |
| `answer_points` | 答案要点（rubric 主项），每条带支撑 chunk | 住宿标准 → hr-003#2；报销流程 → fin-002#1 |
| `citation_required` | 是否必须引用原文 | true |
| `should_abstain` | 是否应拒答 | false |
| `clarify_mode` | ask / assume / none | none |
| `forbidden` | 禁止出现的内容 | 编造金额、编造文号 |
| `max_steps` | 最大工具调用步数 | 4 |
| `relevant_chunk_ids` | 所有 `answer_points.chunk_ids` 的并集，用于检索诊断 | hr-003#2、fin-002#1 |
| `query_type` | 查询类型，便于横向看召回 | 关系推理 |
| `source` | 题型来源，用于检验任务集效度 | real / failure / synthetic |
| `provenance` | 改造自既有负样本时指向来源条目；`source` 仍记 `synthetic`（已重写，不是原句） | negative_samples#0 |
| `mock` | 是否注入故障，用于恢复维度 | true |
| `inject` | 注入计划：工具、第几次调用、模式 | search_kb 第 1 次 empty；第 2 次 timeout |

**任务来源（2026-10-27 定）**

| 来源 | 条数 | 说明 |
|---|---:|---|
| 既有负样本集改造（拒答维度） | 6 | 从 `evaluation/negative_samples.py` 的 20 条里选 6 条改写；它们自带 `why` 与 `fabrication_hint`，`forbidden` 字段可直接落地 |
| 合成（其余四维） | 24 | 从语料结构反推：跨文档冲突、资料缺口、易混淆条款、流程多跳 |

- `source` 字段如实记 `synthetic`：负样本改造的 6 条也**不是真实用户问题**，不冒充 `real`。具体出处（如 `negative_samples#3`）写进可选的 `provenance`，只做追溯，不参与统计分组。
- 本机没有可用的真实查询日志，`real` 暂不出现；将来接真实流量再追加，且只追加不覆盖旧任务。
- 报告按来源分组看通过率——**如果只有 `synthetic` 过得去，说明合成任务太容易**，这是任务集效度最直接的检验。
- 不先写答案再编问题：先有语料里的证据点，再写问题和答案要点。
- 负样本（拒答）与歧义样本（澄清负向）的配比在 §8.8 已定，出题时按配比填，不许后期补。

**任务设计原则**

- 每条任务必须有“工具约束 + 必填参数 + 答案要点”，不能只有问题。工具约束按 §8.3 的四项判，不写精确序列——improved 是 ReAct，序列本来就会偏。
- 每个 `answer_point` 必须带 `chunk_ids`；`relevant_chunk_ids` 是它们的并集，lint 会校验一致性。
- `required_args` 按语义覆盖判，不按字面匹配：Agent 改写 query 用同义词不算错，丢掉一个子问题才算错。判定优先看检索结果是否命中该子问题的 `relevant_chunk_ids`，命中不了才退回 judge 判语义。
- 负样本与歧义样本要占一定比例，否则只能测“会不会检索”，测不出“会不会不乱答”。
- 难度分层：简单 / 中等 / 困难，报告按难度拆。
- 一条任务只归一个主维度，副标签可多个；统计时按主维度汇总，避免重复计数。
- 任务集与检索夹具分离：**不复用 60 条 query 的原文**，但允许把它们的失败案例改写成任务（见上文“任务来源”）；两者不是同一批问句，避免同一批题同时调检索和调 Agent。
- 任务集版本化，新增任务只追加，不覆盖旧任务。
- 澄清维度必须有反向对照（`clarify_mode=none`），防止“见含糊就反问”刷分。
- `mock: true` 的任务只用于恢复维度，统计召回时排除；注入计划对 Agent 不可见。

### 9.2 语料

- 现状：33 chunk / 11 份文档，适合做回归，不适合做能力评测。
- **目标（2026-10-27 定）：60–70 chunk / 20 份文档。** 按任务反推：30 条任务里真正需要独立证据的约 20 条，现有 11 份补 9 份即够；不追求 100+ chunk、30+ 文档。
- **增量注入，不重建语料**（1–2 天，替代原来的“扩到 30+ 文档”）：

| 注入物 | 数量 | 支撑哪一维 |
|---|---:|---|
| 修订版 / 补充通知（与旧制度冲突） | 3 份 | 多步拆解、检索与引用（冲突口径） |
| 明确资料缺口（该主题压根没写） | 2 处 | 拒答与边界 |
| 近义条款（两个都像，只有一个对） | 2 组 | 澄清与追问（`clarify_mode=none` 的对照） |
| 易混淆数字（同一指标两个值，分属不同年度） | 2 处 | 拒答与边界、引用正确率 |

- 注入后约 20 份 / 60–70 chunk；注入物单独列清单，语料 hash 进 manifest。

**冲突不设权威（2026-10-27 定）**：冲突任务只判"**是否指出两份文件不一致**"，不判"以哪份为准"。理由是判定必须客观——一旦要求选权威版本，就得给语料造 `effective_date` / 版本链 / 文档层级，而这些规则本身会成为新的争议点，且和"Agent 会不会看日期"混在一起，归因变脏。将来真有合规需求，再单独立一版规则。
- 来源：公开制度文档 + 自建合成文档；避免使用会泄漏到模型训练集的热门语料。
- 工具层回归夹具：现有 60 条 query 继续使用，但只进 CI；夹具走真实检索，不做 mock。

### 9.3 版本管理

- 任务集、工具描述、baseline 三者版本化；
- 新增任务只追加，不覆盖旧任务；
- 每次报告记录三者版本、语料 hash、模型版本、变体名与运行参数。

**v1 现状（2026-10-27）**：任务集 30 条（`evaluation/agent_tasks.jsonl`，lint 0 error，5 维各 6 条）；语料 `AGENT_CORPUS v1` = 60 chunk / 20 文档，其中 27 chunk / 9 文档是注入物（清单见 `evaluation/agent_corpus.py` 的 `INJECTIONS`）；报告已自动记录 `corpus_version` / `corpus_hash` / 模型名 / 变体 / `runs_per_task`。

**不做 dev/test 切分。** 30 条分 5 维，切出 10 条 test 后每维只剩 2 条——2 条样本的 Wilson 区间是 1/2 → [9.5%, 90.5%]、2/2 → 下界 34%，完美表现也证明不了任何东西（§8.6）。三种做法只有第三种站得住：

| 做法 | 问题 | 结论 |
|---|---|---|
| 全量 30 条出剖面 | test 冻结形同虚设，调 prompt 时已经看过那 10 条 | 否 |
| 只用 test 10 条出剖面 | 每维 2 条，剖面和 §8.6 的 Wilson 论证全部失效 | 否 |
| 不切分，版本冻结 + 双变体差分 | 无 | **采用** |

- **控过拟合靠差分，不靠切分**：baseline 与 improved 的 prompt 都在同一批 30 条上调过，过拟合对两变体等价，所以**差分不受过拟合影响**。
- **“不受过拟合影响”≠“差分可信”**：单次运行下 run-to-run 方差远大于任何 prompt 改动的 delta（实测两批维度翻转 6/30、答案逐字相同 0/30，§8.12）。因此：
  - 每任务 ≥3 次，同时报 `pass@1`（3 次均值）与 `pass^3`（三次全过）；
  - 分维度只做描述，不做显著性宣称（n=6 时 5/6 vs 2/6 的 Fisher p=0.24）；
  - 显著性检验放在**整卷 30 条配对**上（同一批任务跑两变体，McNemar：30 个不一致对需 ≥21:9 才 p<0.05，§8.13）；
  - 单次运行的维度百分比一律标注“单批快照，不可引用”。
- 绝对分数统一标注“内部诊断，n=6/维，不代表泛化”。
- **版本冻结替代 test 集**：v1 发布后不再修改既有任务，新增只进 v2；历史报告永远能对回当时的任务集版本。
- 将来若要对外声称泛化能力，**另建** 10 条外部 held-out（不在这 30 条内），不要从这 30 条里切。

### 9.4 任务集可判性检查（lint）

30 条任务写完一定会出现“答案要点找不到出处”“chunk id 写错”“同一段被八条任务引用”这类问题，而它们直接让任务不可判。lint 是阶段 2 的验收项，不是可选项。

| 检查 | 规则 | 失败含义 |
|---|---|---|
| chunk 存在性 | 每个 `relevant_chunk_ids` 必须在语料中可解析 | id 写错或语料已变更 |
| 正向锚定 | 每个 `answer_point.chunk_ids` 非空，且 chunk 都在语料中 | 该要点没有出处，judge 只能凭感觉判 |
| 反向覆盖 | 每个 `relevant_chunk_ids` 至少出现在一个 `answer_point.chunk_ids` 里 | 有摆设 chunk，recall 诊断会虚高 |
| 锚定一致 | `relevant_chunk_ids` 必须等于所有 `answer_point.chunk_ids` 的并集 | 两处不一致，recall 诊断会漂 |
| 引用集中度 | 单 chunk 被 >5 条任务引用时告警 | 任务设计偏食，剖面会集中在同一段文本 |
| 负样本洁净 | `should_abstain: true` 的任务不得有支撑答案的 chunk | 拒答题其实有答案，测不出编造 |
| 澄清对照配比 | `clarify_mode=ask` 与 `none` 各 ≥2，`assume` ≥1 | 澄清维度防刷分的前提 |
| mock 隔离 | `mock: true` 必须带 `inject`，且不得计入召回统计 | 故障注入污染召回诊断 |
| 元数据完整 | `dimension` / `difficulty` / `source` 非空，五维各 6 条 | 报告无法分组或维度失衡 |
| **要点原子性** | 每个 `answer_point.text` 不得含 `，` `；` `。`（一个要点只能是一个事实） | 一条要点捆两个事实，judge 会在两批之间翻脸（见 §8.10） |

产出：`evaluation/lint_agent_tasks.py`，退出码 0 才允许进阶段 2 验收；lint 报告并入 CI 第 1 层。

### 10.4 双变体实测（2026-10-27）

跑法：30 条 × 3 次 × 2 变体 = 180 次运行，同一语料、同一模型、同一温度；报告见
`docs/evidence/agent_baseline_report3_20261027.json`、`agent_improved_report3_20261027.json`、`agent_compare3_20261027.json`。

| 指标 | baseline | improved | 差 |
|---|---|---|---|
| pass@1（任务均值） | 80.0% | 95.6% | +15.6 点 |
| pass^3（三次全过） | 70.0% | 93.3% | +23.3 点 |
| 恢复与纠错（任务均值） | 22.2% | 83.3% | **+61.1 点（≥ 该维 CI 宽度 53.3，可分辨）** |
| 拒答与边界 | 100% | 94.4% | -5.6 点（N3 有 1 次把“没有扣款条款”答成了确定结论） |
| token / 次运行 | 2,378 | 5,650 | +137.6% |
| 中位延迟 | 6.05 s | 10.81 s | +78.6% |

整卷 30 条配对 McNemar：修好 5 / 弄坏 0，**p=0.0625（未达 0.05）**。
结论必须按两句话写：**恢复维度有可分辨改进；整卷显著性因只有 5 个不一致对而不成立**，
不能把 +14.4 点的整体差说成“全卷显著提升”。

另：本轮修掉两个判定 bug——①improved 用满 `max_steps` 时被 runner 误记
`max_steps_exceeded`，导致 32 条运行被确定性检查判失败（其中 16 条其实是正确拒答）；
②Markdown 答案的 `## 结论` 标题行把“首句”截断，N2#3 的正确拒答被记成 `answered`。
修正后重算确定性检查、复用原 judge 结论，未重烧 judge 调用；原始与修正的对应关系
记录在 `agent_improved_runs3_20261027.json` 的 `note_fix` / `status_fix` 字段。

## 11. 验收标准

### 11.1 Agent

- 能回答企业知识问题，答案带引用；
- 知道什么时候拒答、什么时候澄清；
- 输出契约稳定：答案 + 引用 + 四态状态 + trace（字段见 §6.5）；
- baseline 与 improved 两个变体可切换。

### 11.2 评测

- 30 条任务（lint 退出码 0）、5 个维度、2 个变体、每任务 3 次，全部跑通；
- 报告含五维剖面 + 95% CI、硬门禁结果、横切指标、失败分类；维度不设百分比门禁；剖面只含两变体可比指标；
- 能区分召回失败与 Agent 决策失败；
- judge 不可用、注入未触发时记 **NA / invalid**，不进分母、不记 0；
- judge 稳定性可量化（批内重复一致率 + 跨批判分一致率）；「与人工一致率」在没人抽检前必须标"未做"，不许用自一致率顶替；
- baseline 文件入库，CI 能对比并拦截硬伤；
- 至少有一个“评测改变决策”的案例，允许是否定结论（例如“自评/重试成本 +70%，换不来统计上可分辨的收益，因此不上”）。

### 11.3 工程与文档

- README 首屏能看懂“是什么、怎么跑、五维结果如何”；
- 本设计文档与实现一致，不出现“文档写了但代码没有”的承诺；
- 报告记录模型版本、工具描述版本、任务集版本、语料 hash、变体名、运行参数；
- 任何人 clone 后按 README 能跑出**同一口径**的剖面；模型版本漂移导致的偏差在报告中标注，不承诺逐位复现。

### 11.4 面试可讲

- 能讲清五个维度分别考什么、为什么这么分；
- 能讲清为什么不用一个总分；
- 能讲清 30 条任务怎么来的、难度怎么分层、三条来源各占多少；
- 能讲清非确定性、judge 偏差、人工抽检怎么处理；
- 能讲清为什么不做 dev/test 切分（n 太小，切了等于没切），以及**差分为什么只在整卷配对、多次运行下才可信**（§8.13）；
- 能讲清 trace 契约长什么样、为什么它要比任务集先冻结；
- 能讲清评测改变了哪个决策。

## 12. 风险与边界

| 风险 | 影响 | 应对 |
|---|---|---|
| 维度重叠 | 一条任务同时考多个能力，统计重复 | 只归一个主维度，副标签只做说明；统计按主维度 |
| 每维 6 条太少 | 70% 门槛在 n=6 上不可判定（6/6 下界仅 61.0%） | 删百分比门禁；硬门禁用计数；看板报 95% CI |
| 门槛拍脑袋 | 面试被问穿 | baseline 先行；no-regression = Wilson 下界；improvement delta ≥ CI 宽度 |
| 合成总分 | 掩盖 trade-off | 不做总分；硬门禁 + 五维看板 |
| 自评偏差 | improved 变体的自评可能自欺 | 自评准确率用外部 ground truth 测；人工抽检 |
| 负结果不可信 | self-eval 没收益可能是没触发/没实现 | manipulation check：自评触发率、自评准确率、成本差；只变一个变量 |
| 维度与失败混淆 | 报告解释不清 | 维度分数与失败分布两张表；交叉表只做诊断 |
| mock 泄漏 | 人造检索结果污染召回诊断 | `mock: true` 任务排除出 recall 统计；mock 对 Agent 不可见 |
| 语料太小 | 任务太简单，指标虚高 | 按 §9.2 增量注入到 60–70 chunk；报告标注语料规模与注入清单 |
| LLM judge 偏差 | 分数不可信 | 人工抽检 20%，报一致率；关键项用确定性检查 |
| API 成本 | 全量评测太贵 | PR 只跑冒烟 + 夹具，全量发版前手动 |
| 任务集过拟合 | 指标好看但不可迁移 | 双变体差分（过拟合对两变体等价）+ 版本冻结 + 绝对分数标注“内部诊断”；不用 dev/test 切分 |
| run-to-run 方差 | 单次剖面不可引用，两批差 50 点也可能只是噪声 | 每任务 ≥3 次；分维度只描述；显著性放整卷配对（§8.13）；单次运行标“快照” |
| 维度判据卡在措辞 | 答案只差一句“请确认”，判定就翻 | 判据改判“有没有静默选边”，并要求歧义有代价（§8.2 澄清代价） |
| 出题来源单一 | 30 条都在考同一类东西，剖面虚高 | `source` 字段 + 报告按来源分组；三条来源各占约 1/3 |
| trace 契约反复 | 判分代码返工，报告口径前后不一致 | §6.5 先冻结，阶段 1 就产出真 trace；改契约必须重跑 baseline |
| 语料造不出来 | 恢复/澄清维度没有证据点，任务写成空题 | 按 §9.2 的注入表逐项落；注入物清单进 manifest |
| 过度承诺 | 面试被问穿 | 明确边界：只评本项目 Agent 与工具，不称“通用 benchmark” |
| 工程膨胀 | 变成半个平台 | 只读工具、不做写操作、不做多租户、不先做 dashboard |

## 13. 对外表述

### 13.1 一句话

一个企业知识问答 Agent，外加一套 30 条任务的五维能力评测：检索与引用、多步拆解、拒答与边界、澄清与追问、恢复与纠错；硬门禁只设在零容忍项上，五维剖面做看板，失败可归因，评测可回归。

### 13.2 简历三条主线

1. **Agent 本身**：企业知识问答，工具只读，会选工具、多跳、引用、拒答、澄清、自评；对外只暴露 `answer + citations + status + trace` 一个契约。
2. **多维评测**：30 条任务 × 5 个能力维度；每任务 3 次；一份能力剖面 + 95% CI，不合成总分；**不做 dev/test 切分，靠整卷配对差分 + 版本冻结控过拟合与方差**。
3. **决策与回归**：baseline vs improved 对比，得出“哪一维涨了、成本涨了多少”；硬门禁只设零容忍项，维度只做看板；允许否定性结论。

### 13.3 面试必答的九个问题

1. 五个维度为什么这么分？每个维度考什么？
2. 30 条任务怎么来的？难度怎么分层？负样本/歧义样本占多少？
3. 怎么定义“成功”？rubric 谁定的？一致性怎么保证？
4. Agent 非确定性怎么处理？跑几次？pass@1 还是 pass^3？
5. LLM-as-judge 的偏差怎么校准？和人工一致率多少？
6. 样本量这么小，你怎么设门槛？
7. **为什么不做 dev/test 切分？**（答：30 条切完每维 2 条，2/2 的 Wilson 下界只有 34%，切了等于没切；改用整卷配对差分 + 版本冻结，但差分必须 ≥3 次/任务、检验放整卷 30 条，§9.3 / §8.13）
8. **所有指标都从 trace 算，trace 是什么样的？**（答：§6.5，先于任务集冻结；改契约要重跑 baseline）
9. 评测结果改变了什么决策？有没有负结果？

### 13.4 不要说的话

- 不要说“两套测评集”——只有一套任务集，五个观测维度；
- 不要说“通用 benchmark”；
- 不要说“总分 X 分”——用剖面 + 每维 95% CI；
- 不要说“每维 ≥70%”——n=6 时 6/6 的 Wilson 下界只有 61.0%；
- 不要说“test 集上 90%”——10 条 test 切完每维 2 条，这个数字没有意义；本项目不做切分；
- 不要说“工具序列完全匹配才算对”——improved 是 ReAct，判的是约束四项；
- 不要说“完全复现”——只能说“同一口径、可追溯”；
- 不要用单次点估计卡门禁；
- 不要在 baseline 跑出来之前说“Agent 能力评测”；
- 不要把“跑过 20 条 prompt”说成“评测体系”；
- 不要把“单次成功”说成“稳定可用”。

### 13.5 一句加分的话

> 我知道 30 条样本测不出 5 个点的差异，所以门禁只设在零容忍项上，维度剖面只做趋势判断。

## 14. 术语

| 术语 | 含义 |
|---|---|
| 工具层 | Agent 可调用的检索/回查/文档浏览能力 |
| Agent 线 | 被测的企业知识问答 Agent |
| 评测线 | 出题、跑 Agent、判分、出剖面的评测体系 |
| 维度 | 一种能力，如“多步拆解”；不是指标 |
| 指标 | 对能力的测量，如“子问题覆盖率” |
| 横切指标 | 跨维度统一的成本/稳定性指标，如步数、延迟、token |
| 能力剖面 | 五个维度各自的分数 + 95% CI，不设百分比门禁，不是单一总分 |
| pass@1 | 单次运行通过率的均值（3 次取任务均值，不是只看第一次）；每次运行都报 |
| pass^3 | 三次运行全部成功的比例，衡量稳定性；仅全量报告产出 |
| 回归夹具 | 工具层的 60 条 query，只进 CI，不进主叙事 |
| 评测效度 | 评测是否真的测到了想测的能力，而非运气或泄漏 |
| Wilson 下界 | 小样本比例的 95% 置信下界；n=6 时 6/6 也只有 61.0% |
| 硬门禁 | 零容忍/确定性项，用计数判定，不用百分比 |
| 看板 | 维度分数 + 95% CI，只报趋势，不设门禁 |
| 故障注入 | 按任务与调用次数注入 empty/timeout/500/truncated |
| manipulation check | 证明自评/重试真的触发了，否则负结果可能是 bug |
| 维度归因 | 维度分数按设计意图归主维度，不等于失败原因 |
| baseline | 用于回归对比的基准报告与指标文件 |
| tool_constraints | 工具约束四项：必含、调用次数范围、必要先后、禁含；不判精确序列 |
| trace | Agent 每步的工具、参数、结果 id、耗时、自评；判分唯一数据源（§6.5） |
| 剖面指标 | 两个变体都能算、可直接比较的指标；自评三项属诊断明细 |
| 差分可信 | 同批任务上调过的两个变体，过拟合等价；但只对过拟合免疫，仍需 ≥3 次/任务与整卷配对检验（§8.13） |
| badcase 回灌 | 失败任务落成记录，修复后转为回归任务（§8.10） |
| 任务集 lint | 检查 chunk 锚定、要点覆盖、澄清配比、mock 隔离等可判性条件（§9.4） |
